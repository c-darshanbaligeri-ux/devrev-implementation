Writing Good Test Cases

Good test case:Input: "What's our refund policy for Enterprise customers in the EU?"
Expected Output: "Enterprise EU customers have a 60-day refund window. To initiate a refund, contact your account manager or submit a request through the billing portal. Refunds are processed within 5-10 business days."
Remarks: Must reference the 60-day window and the two initiation methods.

Bad test case:Input: "Refund policy"
Expected Output: "Something about refunds"
Remarks: None

The expected output should be specific enough that correctness can be objectively evaluated.

Every explicit user question in the conversation is identified

Each question is scored:

1.0 = Fully answered, customer's issue resolved

0.5 = Temporary workaround offered, not complete solution

0.0 = Not answered or only partially addressed

Session score = average of all question scoresHow Accuracy Is Calculated

Every claim in the agent's response is compared against raw source data

Each response is scored:

5 = Completely accurate, everything matches sources

4 = Mostly accurate, minor gaps

3 = Mixed, some correct, some diverges

2 = Mostly inaccurate, several errors

1 = Completely inaccurate, contradicts sources or fabricates

Session score = average of all response scoresWhich Metric to Fix First

Priority: Task Success > Accuracy1. Task Success LOW → Fix task success immediately. Ignore accuracy.
   - Add missing knowledge sources
   - Improve agent instructions
   - Add skills for common action patterns

2. Task Success HIGH, Accuracy LOW → Audit knowledge sources.
   - Your agent solves problems but with wrong information (worst case)
   - Check for outdated articles
   - Verify source-document alignment
   - Add guardrails against fabrication

3. Task Success HIGH, Accuracy HIGH → You're in good shape. Monitor and iterate.Common Misconceptions

Misconception

Reality

"High task success means the agent is good"

If accuracy is low, you're efficiently providing wrong information

"If info comes from the KB, accuracy should be 100%"

The KB might be outdated, or the agent might misinterpret it

"These metrics replace satisfaction surveys"

They complement surveys — a customer might rate 5/5 for a wrong answer4. Observe: Monitoring Live AgentsAnalytics Dashboard

2. Test 15-20 inputs in Playground
3. Review execution traces for each
4. Identify and fix top 3 issues
5. Repeat steps 2-4 until satisfiedPre-Publish Phase1. Create comprehensive bulk test dataset (30-50 test cases)
2. Run bulk test with both evaluators
3. Review failures — categorize by type:
   - Knowledge gap (missing source) → Add knowledge or articles
   - Instruction gap (agent didn't follow rules) → Update instructions
   - Skill issue (wrong parameters, wrong skill chosen) → Fix skill config
   - Guardrail miss (safety rule not triggered) → Strengthen guardrail description, check applies_to covers the right stage (input/output/both), verify agent_guardrails_enabled in archon-policy
4. Fix issues and re-run bulk test
5. Repeat until pass rate > 90%
6. PublishPost-Publish Phase1. Enable analytics
2. Review sessions daily for the first week
3. Check for patterns in low-performing sessions
4. Create a new draft with fixes
5. Run bulk test against new draft
6. Publish updated version
7. Transition to weekly review cadenceVersion Management

Failure

How to Diagnose

Fix

Agent hallucinates

Check trace → did it find relevant knowledge? If not, it made things up

Add knowledge sources, improve instructions to require source-backed answers

Agent uses wrong skill

Check trace → what was the reasoning? Did it misread the skill description?

Rewrite skill description with clearer trigger conditions

Agent ignores guardrail

Check trace → was the guardrail evaluated? Did it trigger but get overridden?

Make guardrail more specific, or move to a higher-priority position

Also check: Is applies_to set correctly? If the guardrail only checks ["input"] but the issue is in the agent's output, add "output" to applies_to. Verify neuron.agent_guardrails_enabled is true in archon-policy for this org.

Agent too verbose

Check trace → is it retrieving too much context?

Narrow knowledge sources, add length constraints to instructions

Agent too terse

Check trace → is it not retrieving enough? Did it find relevant info?

Broaden knowledge sources, add completeness requirements to instructions

Agent inconsistent

Compare traces for similar inputs → different retrieval results?

Add source-preference rules, reduce knowledge scope

Agent slow

Check trace → which step takes longest?

Optimize skill workflows, reduce knowledge object types, check external API latency7. Testing ChecklistBefore First Publish

Tested 15+ inputs in Playground covering all categories

Reviewed execution traces for each test

Verified skill selection is correct for each input type

Verified knowledge retrieval returns relevant results

Tested guardrail triggers with adversarial inputs

Created bulk test dataset (30+ test cases)
