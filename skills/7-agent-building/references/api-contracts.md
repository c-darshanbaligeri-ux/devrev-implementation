# DevRev AI Agent API Contracts

> **Purpose:** Authoritative reference for every confirmed API schema difference, pitfall, and breaking behaviour discovered through live API testing. Read this before writing any create/update payload.

> **Source:** Empirically verified against `api.devrev.ai/internal` (devo: `dvrv-in-1`) on 2026-06-01.

---

## Quick Cheat Sheet

| Field / Situation | `ai-agents.create` | `ai-agents.update` |
|---|---|---|
| `slug` | ❌ Invalid field | ❌ Invalid field |
| `name` | Optional (auto-generated) | Updatable |
| `goal` | **Required** | Optional |
| `guidance` | Optional string | Optional string — `null` rejected |
| `guardrails` wrapper | Plain array `[...]` | `{"set": [...]}` object |
| `guardrails.topic_boundary` fields | **Flat** (no nesting) | **Flat** (no nesting) |
| `skills` wrapper | Plain array `[...]` | `{"set": [...]}` object |
| `skill.trigger.operation` | String ID | String ID only |
| `skill.trigger.plan` | String ID | String ID only |
| `skill.trigger.workflow` | String ID | String ID only |
| `memory_config` | Optional object | Optional object — `null` rejected |
| `id` field for get/update | N/A | DON ID **or** `display_id` (ai_agent-N) |

## Issue #1 — `slug` is not a valid field on create or update

**Symptom:**
```json
{ "type": "invalid_field", "message": "Bad Request", "debug_message": "Invalid field: slug" }
```

**Root cause:** The slug is auto-generated by the API from the agent name. It cannot be set by the caller.

**Fix:** Remove `slug` from all create/update payloads. Use `name` instead.

```json
// ❌ Wrong
{ "name": "My Agent", "slug": "my-agent", "goal": "..." }

// ✅ Correct
{ "name": "My Agent", "goal": "..." }
```

## Issue #2 — `skills` must be an object `{"set": [...]}` on update, not a plain array

**Symptom:**
```json
{ "type": "unexpected_json_type", "message": "Bad Request", "debug_message": "Unexpected JSON type for field: 'skills', expected: 'OBJECT', actual: 'ARRAY'" }
```

**Root cause:** The update API uses a collection-patch pattern. Fields that can be added/removed are wrapped in a `{"set": [...]}` envelope. The create API does not use this pattern.

**Fix:**

```json
// ❌ Wrong on UPDATE
{ "id": "...", "skills": [ { "name": "FetchObjectContext", ... } ] }

// ✅ Correct on UPDATE
{ "id": "...", "skills": { "set": [ { "name": "FetchObjectContext", ... } ] } }

// ✅ Correct on CREATE (plain array is fine)
{ "name": "My Agent", "skills": [ { "name": "FetchObjectContext", ... } ] }
```

---

## Issue #3 — `guardrails` must be `{"set": [...]}` on update, not a plain array

**Symptom:**
```json
{ "type": "unexpected_json_type", "message": "Bad Request", "debug_message": "Unexpected JSON type for field: 'guardrails', expected: 'OBJECT', actual: 'ARRAY'" }
```

**Root cause:** Same collection-patch pattern as `skills`.

**Fix:**

```json
// ❌ Wrong on UPDATE
{ "id": "...", "guardrails": [ { "type": "topic_boundary", ... } ] }

// ✅ Correct on UPDATE
{ "id": "...", "guardrails": { "set": [ { "type": "topic_boundary", ... } ] } }

// ✅ Correct on CREATE
{ "name": "My Agent", "guardrails": [ { "type": "topic_boundary", ... } ] }
```

## Issue #4 — `topic_boundary` fields must be flat, not nested

**Symptom:**
```json
{ "type": "invalid_field", "message": "Bad Request", "debug_message": "Invalid field: topic_boundary" }
```

**Root cause:** The GET response returns guardrails with `topic_boundary` as a nested object. However, the write API (`set-ai-agent-guardrail`) uses a discriminated union where the type-variant fields (`topic_name`, `description`) are merged flat — at the same level as `type`, not nested.

Developers who copy a guardrail from a GET response and send it back in an update get this error.

**Fix:**

```json
// ❌ Wrong — this is the GET response shape, not the write shape
{
  "type": "topic_boundary",
  "applies_to": ["input"],
  "enabled": true,
  "default_message": "...",
  "topic_boundary": {
    "topic_name": "My Topic",
    "description": "Only respond to questions about..."
  }
}

// ✅ Correct — flat, for both CREATE and UPDATE
{
  "type": "topic_boundary",
  "applies_to": ["input"],
  "enabled": true,
  "default_message": "...",
  "topic_name": "My Topic",
  "description": "Only respond to questions about..."
}
```

This applies to both `ai-agents.create` and `ai-agents.update`.

## Issue #5 — Skill trigger `operation` / `plan` must be a string ID on update

**Symptom:**
```json
{ "type": "unexpected_json_type", "message": "Bad Request", "debug_message": "Unexpected JSON type for field: 'operation', expected: 'STRING', actual: 'OBJECT'" }
```

**Root cause:** The GET response returns fully hydrated operation/plan objects (with `id`, `display_id`, `name`, etc.). The write API only accepts the DON ID as a plain string.

**Fix:**

```json
// ❌ Wrong — hydrated object from GET response
{
  "name": "FetchObjectContext",
  "trigger": {
    "operation": {
      "id": "don:integration:dvrv-in-1:operation/devrev.fetch_object_context",
      "display_id": "...",
      "name": "Fetch Object Context"
    }
  }
}

// ✅ Correct — string ID only
{
  "name": "FetchObjectContext",
  "trigger": {
    "operation": "don:integration:dvrv-in-1:operation/devrev.fetch_object_context"
  }
}

// ✅ Correct — plan trigger also uses string ID
{
  "name": "my-plan-skill",
  "trigger": {
    "plan": "don:core:dvrv-in-1:devo/29qpwaLo99:ai_agent_plan/5"
  }
}
```

This applies on both create and update.

## Issue #6 — Skill trigger `workflow` must be a string ID, not an object

**Symptom:**
```json
{ "type": "unexpected_json_type", "message": "Bad Request", "debug_message": "Unexpected JSON type for field: 'workflow', expected: 'STRING', actual: 'OBJECT'" }
```

**Root cause:** A third trigger type exists alongside `operation` and `plan`: the `workflow` trigger. It follows the exact same GET-vs-write asymmetry — the GET response returns a fully hydrated `workflow` object (with `id`, `display_id`), but the write API accepts only the DON ID string.

**Fix:**

```json
// ❌ Wrong — hydrated object from GET response
{
  "name": "MyWorkflowSkill",
  "trigger": {
    "workflow": {
      "id": "don:integration:dvrv-in-1:devo/29qpwaLo99:workflow/40",
      "display_id": "workflow-40"
    }
  }
}

// ✅ Correct — string ID only
{
  "name": "MyWorkflowSkill",
  "trigger": {
    "workflow": "don:integration:dvrv-in-1:devo/29qpwaLo99:workflow/40"
  }
}
```

Workflow-triggered skills follow the ID pattern:
```
don:integration:dvrv-in-1:devo/<devo-id>:workflow/<n>
```

> **Skill name coherence:** When a skill is named `FetchObjectContext` or any other native operation name but is triggered by a **custom workflow**, this creates confusion during debugging. Always name the skill to reflect what it actually does in the agent (e.g. `FetchConversionRules`, `RunPipeline`), not the generic DevRev operation type.

## Systematic Pre-Flight Checklist

Before sending any `ai-agents.create` or `ai-agents.update` payload, verify:

**Create:**
- [ ] No `slug` field
- [ ] `guardrails` is a plain array `[...]`
- [ ] Each guardrail's `topic_name` and `description` are **flat** (not nested under `topic_boundary`)
- [ ] `skills` is a plain array `[...]`
- [ ] Each skill's `trigger.operation`, `trigger.plan`, or `trigger.workflow` is a **string** (DON ID), not an object
- [ ] Each skill's name accurately describes its function (not a generic DevRev type name if it runs a custom workflow)

**Update:**
- [ ] `id` field is present and is a full DON ID
- [ ] No `slug` field
- [ ] `guardrails` is wrapped: `{ "set": [...] }`
- [ ] Each guardrail's `topic_name` and `description` are **flat** (not nested under `topic_boundary`)
- [ ] `skills` is wrapped: `{ "set": [...] }`
- [ ] Each skill's `trigger.operation`, `trigger.plan`, or `trigger.workflow` is a **string** (DON ID), not an object
- [ ] Each skill's name accurately describes its function

## Error → Fix Reference

| Error message | Field | Fix |
|---|---|---|
| `Invalid field: slug` | `slug` | Remove the `slug` field |
| `Unexpected JSON type for field: 'skills', expected: 'OBJECT', actual: 'ARRAY'` | `skills` | Wrap in `{"set": [...]}` (update only) |
| `Unexpected JSON type for field: 'guardrails', expected: 'OBJECT', actual: 'ARRAY'` | `guardrails` | Wrap in `{"set": [...]}` (update only) |
| `Invalid field: topic_boundary` | guardrail `topic_boundary` | Flatten `topic_name` and `description` to top level |
| `Unexpected JSON type for field: 'operation', expected: 'STRING', actual: 'OBJECT'` | skill trigger | Use string ID, not the full hydrated object |
| `Unexpected JSON type for field: 'plan', expected: 'STRING', actual: 'OBJECT'` | skill trigger | Use string ID, not the full hydrated object |
| `Unexpected JSON type for field: 'workflow', expected: 'STRING', actual: 'OBJECT'` | skill trigger | Use string ID, not the full hydrated object |
| `Unexpected JSON type for field: 'guidance', expected: 'STRING', actual: 'NULL'` | `guidance` | Omit the field or use `""` — do not send `null` |
| `Unexpected JSON type for field: 'memory_config'` | `memory_config` | Omit the field — do not send `null` |
| `limit must be > 0` | `limit` in list | Use limit between 1 and 99 |
| `invalid val for PerPage, should be less than '100'` | `limit` in list | Maximum allowed limit is 99 |
| `Missing required field: goal` | `goal` | `goal` is required on create |
| `Invalid field: agent_id` | versions.list filter | Use `"agent"` not `"agent_id"` |
| `ai agent id is required` | versions.list | `agent` filter is required on versions.list |
| `route not found` | plans.get / plans.list | These endpoints do not exist; plan definitions are not fetchable |

## Schema Summary: Create vs Update

```
ai-agents.create request body:
  name: string                        (required)
  goal: string
  guidance: string
  guardrails: set-ai-agent-guardrail[]    ← plain array
  memory_config: object
  skills: ai-agent-skill[]               ← plain array

ai-agents.update request body:
  id: string (DON ID)                 (required)
  goal: string
  guidance: string
  guardrails:                            ← {"set": [...]} wrapper
    set: set-ai-agent-guardrail[]
  memory_config: object
  skills:                                ← {"set": [...]} wrapper
    set: ai-agent-skill[]

set-ai-agent-guardrail (write, flat):
  type: "none" | "topic_boundary"
  applies_to: ("input" | "output")[]
  enabled: boolean
  default_message: string
  topic_name: string                     ← flat (not nested)
  description: string                    ← flat (not nested)

agent-guardrail (read/GET response, nested):
  type: "topic_boundary"
  applies_to: (...)[]
  enabled: boolean
  default_message: string
  topic_boundary:                        ← NESTED in GET only
    topic_name: string
    description: string

ai-agent-skill (write):
  name: string
  act_as_user: boolean
  description: string
  needs_approval: boolean
  trigger:
    operation: string (DON ID)           ← string, not object  [native DevRev ops]
    OR
    plan: string (DON ID)               ← string, not object  [custom agent plans]
    OR
    workflow: string (DON ID)           ← string, not object  [custom org workflows]

Trigger type DON ID patterns:
  operation  → don:integration:dvrv-in-1:operation/devrev.<slug>
               don:integration:dvrv-in-1:devo/<id>:operation/custom_object.<slug>
  plan       → don:core:dvrv-in-1:devo/<id>:ai_agent_plan/<n>
  workflow   → don:integration:dvrv-in-1:devo/<id>:workflow/<n>
```

## Guidance Quality: Common Corruption Patterns

When fetching or writing the `guidance` field, watch for these patterns that silently degrade agent behavior:

| Pattern | Source | Fix |
|---|---|---|
| `&nbsp;` entities throughout text | Pasted from HTML/rich text | Strip all `&nbsp;` — they render as visible text in the agent |
| `═══...═══` decorative borders | Copied from formatted doc | Replace with `---` markdown dividers |
| `[S.No](http://S.No)` markdown link artifacts | Auto-linked plain text | Replace with plain `S.No` |
| Truncated rules mid-sentence | Copy-paste truncation | Identify and complete using context from surrounding rules |
| References to "operator appendix" without an appendix | Template residue | Replace with inline actionable rules |
| Excessive blank lines (3+) inside cells | Formatting | Collapse to max 1 blank line |

**Scan script (run on any guidance text before publishing):**
```python
import re

def audit_guidance(text):
    issues = []
    if '&nbsp;' in text:
        issues.append(f"  &nbsp; count: {text.count('&nbsp;')}")
    if '═' in text:
        issues.append(f"  === borders: {text.count('═')}")
    if re.search(r'\[.*?\]\(http', text):
        issues.append("  markdown link artifacts found")
    # Detect truncated sentences (ends with ", " or comma before a blank line)
    if re.search(r',\s*\n\s*\n\s*[A-Z]', text):
        issues.append("  possible truncated rule (line ends with comma before blank line + new section)")
    if 'operator appendix' in text.lower():
        issues.append("  references 'operator appendix' — check if appendix actually exists")
    return issues

issues = audit_guidance(open('guidance.txt').read())
for i in issues:
    print(i)
```

## Endpoint Reference (Empirically Verified)

All endpoints use `POST /internal/<endpoint>` with `Authorization: <ORG_PAT>` unless noted.

| Endpoint | Required field(s) | Notes |
|---|---|---|
| `ai-agents.list` | — | `limit` default works; max 99; empty body OK |
| `ai-agents.get` | `id` | Accepts DON ID **or** `display_id` format (`ai_agent-N`) |
| `ai-agents.create` | `goal` | `name` is optional (auto-assigned if omitted); `goal` is required |
| `ai-agents.update` | `id` | Accepts DON ID **or** `display_id` format; partial update preserves unmentioned fields |
| `ai-agents.delete` | `id` | Accepts DON ID; returns `{}` on success |
| `ai-agents.versions.list` | `agent` | `agent` = DON ID of agent (NOT `agent_id`); filter is REQUIRED |
| `ai-agents.versions.get` | `id` | `id` = version DON ID |
| `ai-agents.plans.list` | — | ❌ **Route not found** — endpoint does not exist |
| `ai-agents.plans.get` | — | ❌ **Route not found** — endpoint does not exist |

> Agent plan definitions (for `trigger.plan` skills) **cannot be fetched** via the current API. There is no known endpoint for `ai_agent_plan` objects.

## Behavioral Rules Discovered by Testing

### `ai-agents.list` constraints

- **Minimum limit:** 1 (limit=0 returns `bad_request: "limit must be > 0"`)
- **Maximum limit:** 99 (limit=100 returns `bad_request: "invalid val for PerPage, should be less than '100'"`)
- **Default:** empty body `{}` returns all agents (up to 99) with no error
- **Strict unknown fields:** any unknown field in the request body returns `invalid_field` (no forward-compat tolerance — do NOT add exploratory fields)
- **Cursor pagination:** returns `next_cursor` when more results exist; pass as `"cursor": "<value>"` in next request

### `ai-agents.get` / `ai-agents.update` — ID formats accepted

Both `get` and `update` accept two forms of the `id` field:

```json
// ✅ DON ID (canonical form)
{ "id": "don:core:dvrv-in-1:devo/29qpwaLo99:ai_agent/1" }

// ✅ display_id (shorthand, undocumented)
{ "id": "ai_agent-1" }

// ❌ slug (not accepted in id field)
{ "id": "computer" }
```

### `ai-agents.create` — required fields

**Only `goal` is required.** `name` is optional (auto-generated as `ai_agent-N` if omitted).

```json
// ✅ Minimal valid create payload
{ "goal": "Describe what this agent does." }

// ❌ name alone fails: missing_required_field: goal
{ "name": "My Agent" }
```

### `ai-agents.update` — partial update behavior

- Unmentioned fields are preserved (the update is **additive/selective**, not a full replace)
- Sending `skills: {set: []}` clears all skills; sending no `skills` key preserves existing skills
- Sending `guardrails: {set: []}` clears all guardrails; sending no `guardrails` key preserves them
- `ai-agents.update` does **NOT** create a new version — the `default_version_id` is unchanged after an update

### GET response — absent vs. empty fields

The GET response **omits** the `skills` and `guardrails` keys entirely when they are empty:

```json
// Agent with no skills or guardrails
{
  "agent": {
    "id": "...", "display_id": "...", "goal": "...",
    // ← NO "skills" key
    // ← NO "guardrails" key
  }
}

// Agent with skills/guardrails
{
  "agent": {
    "skills": [...],    // ← present only when non-empty
    "guardrails": [...]
  }
}
```

This is handled safely by the `jq` patterns in `create-agent.sh` (`[]?` operator) and `get-agent.sh`.

### `guidance` field constraints

- `guidance: null` is **rejected** on update: `"Unexpected JSON type for field: 'guidance', expected: 'STRING', actual: 'NULL'"`
- `guidance: ""` (empty string) **is accepted**
- When an agent has no guidance set, the GET response includes `"guidance": null` — the `create-agent.sh convert` command strips this key to avoid the update error

### `memory_config` constraints

- `memory_config: null` is **rejected** on update: `"Unexpected JSON type for field: 'memory_config'"` 
- `memory_config` is **strict** — unknown fields inside the object return `invalid_field`
- Valid fields: `memory_store_enabled` (boolean), `recall_chats_enabled` (boolean)

### `ai-agents.versions.list` — correct field names

```json
// ✅ Correct
{ "agent": "don:core:dvrv-in-1:devo/<id>:ai_agent/<n>", "limit": 10 }

// ❌ Wrong — invalid_field errors
{ "agent_id": "...", "limit": 10 }  // → "Invalid field: agent_id"
{ "id": "...", "limit": 10 }        // → "Invalid field: id"
```

The response field is `agent_versions` (array), not `ai_agent_versions`.  
The `agent` filter is **required** — omitting it returns `bad_request: "ai agent id is required"`.

### `ai-agents.delete`

Discovered endpoint — not previously documented. Accepts the agent DON ID:

```json
POST /internal/ai-agents.delete
{ "id": "don:core:dvrv-in-1:devo/<id>:ai_agent/<n>" }
// Returns: {} on success
```
